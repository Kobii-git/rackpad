# Rackpad v1.8.2-beta.5 acceptance matrix

This tester beta is based on `v1.8.2-beta.4`. Use the `v1.8.2-beta.5`
prerelease image and installer files from that same Git tag. Docker remains the
supported general deployment; native LXC is experimental. No issue is closed
by publication or by automated tests alone.

## Known beta limitations and validation

Local `check:full` passed all 37 browser tests. The final label/focus change also
passed the complete standard gate (299 server and 90 client tests), seven
focused browser cases, and independent review. Proxmox fixtures, shell checks,
all three Compose renders, npm audit, and the repository Trivy scan passed.

Screenshot determinism remains unresolved: separate Linux capture comparisons
failed on small differences in the audit, SNMP device, and Device Types screens;
the unchanged beta.4 comparison passed. No screenshot tolerance was relaxed.
The local container scan reported 51 HIGH and 3 CRITICAL OS-package findings
with no fixed versions reported by Trivy. The fixable-vulnerability gate passed;
this does not mean the container has no known advisories.

Real PVE guest testing, the seven-day soak, and community feature acceptance
remain outstanding. Stacked switches are not included in this beta.

## Upgrade and recovery

Retain the encryption key and capture a database/configuration backup. Read the
[security upgrade notes](v1.8.2-beta.4-test-notes.md), including explicit proxy
trust, OIDC administrator mapping, session/role rechecking, and trap opt-in.
Beta.5 keeps schema 50. Test both beta.3 -> beta.5 (security migration) and
beta.4 -> beta.5 (no schema change) on disposable data. Rollback requires the
matching previous application and pre-upgrade database/configuration snapshot.
Do not start beta.3 or older code against schema 50 or remove existing backups.

## Rack Studio: issues #139 and #148

Use a disposable existing-lab upgrade and a new synthetic lab. Record browser,
viewport, candidate version, upgrade/fresh status, and PASS/FAIL for each row.
The automated `rackCableFixture` creates a synthetic 12U rack, a patch panel at
U10, a switch at U9, 24-column faces, and 24 green matching front patch cords.
The browser suite exercises the actual APIs and stores a review screenshot in
its temporary test output; it does not use a reporter's inventory.

### Reproduce the synthetic scenario

From the candidate checkout with Node 22, install dependencies and Chromium,
then run the focused acceptance cases:

```bash
npm ci
npx playwright install chromium
node --import tsx --test src/lib/cable-routing.test.ts src/lib/hardware-template-builder.test.ts
npx playwright test e2e/app.spec.ts --grep '24 short patch cords|patch-panel hardware templates|Rack Studio places rack-top|Device Types workspace'
```

The browser harness creates and removes its own temporary database. To inspect
interactively, add `--debug` to that Playwright command and pause before cleanup.
For the manual upgrade pass, first create synthetic inventory on beta.3 or
beta.4: a 12U rack, panel at U10, switch at U9, and 24 matching front-port links.
In Device types, start with Patch panel, set the port block to 24 ports,
24 columns, and one row on each face, then apply the matching port/hardware
templates. Save a manual cable waypoint and an inherited server-child template.
Capture a database/configuration snapshot, upgrade the disposable instance,
and perform every acceptance row below. Move a separate synthetic device to the
rack top so the original panel/switch fixture remains available for comparison.

| Case | Acceptance |
| --- | --- |
| Old cabling | Existing device/port/link IDs and both endpoints survive upgrade. |
| Short patch cords | In Smooth mode, 24 nearby matching ports have distinct direct curved cords. No detour through rack gutters is needed. |
| Long/blocked cords | More than 4U, obstructed, cross-rack, and hidden-face/room connections retain appropriate gutter/handoff routes. |
| Interaction/export | Hover/select one cord, zoom, filter, toggle Orthogonal, and reload. Endpoints and saved preferences remain correct; SVG and PNG retain the same shapes. |
| Manual routes | Saved room/face waypoints keep their coordinates after reload and rack movement. Focused views do not replace explicitly routed links with short automatic cords. |
| Placements | Check direct, fractional-width, shelf, rotated, side, rack-top, and loose equipment on front/rear/both views. |
| Rack top | Place equipment on the rack top without consuming U height; move, undo/redo, and verify overlap rejection and export. |
| Inherited templates | A server child type lists/applies its inherited server template; child defaults override parent defaults. |
| Patch starter | Separate front/rear starters each contain ports 1–24. |
| Face editing | Set Columns=24 and one row in the port-block editor. Repeatedly update rear/front blocks with the same name; the opposite face remains intact. |
| Binding | Apply the built-in 24-port patch template and matching hardware template: 48 bindings, zero unmapped ports, 24 connectors per face. |
| Trace | Trace every front/rear pair in both directions, including a custom descendant of patch_panel. |
| Legacy template | Edit one face of a stored legacy block; preserve the other face and existing device snapshots. |

Issue #148 needs explicit confirmation of starter, independent editing, binding,
and all-pair tracing. Issue #139 also needs acceptance of the cable appearance,
inherited templates, rack-top behavior, and upgraded inventory. Screenshots may
illustrate failures, but must not disclose private addresses or credentials.

## Native Proxmox: issue #138

You/community testers own this evidence. Use disposable PVE 9.x AMD64 hosts
with separate unprivileged Debian 13 and Ubuntu 24.04 guests. Follow the
[tagged installer procedure](../PROXMOX_NATIVE_LXC.md). Do not convert a guest
to privileged mode or change host security to force a test to pass.

| Case, repeated on both guest OSs | Required observation |
| --- | --- |
| Fresh install | Active service; correct version and immutable release path; first administrator can sign in. |
| Hardening | Root-owned read-only release, service-writable data only, environment mode 0640, base AF_NETLINK allowed, base AF_PACKET absent. |
| Application | Health/auth/SPA, Proxmox and Hyper-V collector downloads, local password reset, logical/native backup and restore. |
| Configuration | Custom port 3100 works, restore port 3000 afterward; configuration/key/data survive reboot and update. Compare sensitive values locally, report only match/mismatch. |
| Discovery | Safe mode clears capabilities. Advanced mode works or truthfully refuses the outer-LXC restriction; AF_PACKET occurs only in its opt-in drop-in. |
| Traps | UDP 1162 remains closed by default; enabling discovery does not enable traps. |
| Forward updates | Test beta.3 -> beta.5 and beta.4 -> beta.5 on separate retained clones. Verify schema 50, inventory, credentials, OIDC re-login, and administrator access. |
| Same target/downgrade | Repeating beta.5 is a no-op with unchanged service PID; older target is rejected before download/downtime. |
| Download/build failure | Inject failure on a disposable clone before activation; existing service, symlink, database, configuration, and operational assets remain intact. |
| Snapshot failure | Fail snapshot preparation on a disposable clone; verify truthful failure, original application/data preservation, and service recovery. |
| Post-migration/startup failure | Inject candidate-only failure, then verify automatic restoration of the previous code, database, environment, unit/drop-in, helper origin and core pin; reboot the restored guest. |
| Soak | Seven consecutive days of monitoring, integration status, backups, and discovery without unresolved service, privilege, update, or data-loss defects. |

Use the repository's 14 isolated update/rollback scenarios to identify the
failure points before rehearsing them on guest clones. Never inject faults into
production guests. Record exactly how each guest fault was introduced and
removed; a fixture pass does not count as a real-guest pass. If a candidate
changes materially, repeat affected tests and restart its seven-day soak.

## Release and issue gates

Run `check`, `check:full`, deterministic screenshots, Proxmox fixtures, shell
checks, all Compose renders, npm audit, and Trivy. Review the complete diff,
including geometry/export parity and deployment/rollback documentation.

Prepare issue updates with those results and clearly separate automated
coverage from community acceptance. Publishing, posting, closing issues,
deployment, and upstream submission require separate authorization.

Stable 1.8.2 requires the Rack Studio confirmations and complete guest matrix /
seven-day soak. Only then start issue #146 from the validated stable baseline
for 1.9.0. Its migration is the next unused version (currently 51), never 50.
The approved scope remains one logical switch with ordered members, labelled
member MACs/serials, same-device port assignments, derived height, generic
member faces, and atomic lab-scoped updates/backups. No stack code is included
in this candidate.

Official Community Scripts listing remains separate: recheck the current age,
adoption, release, maintenance, and real-guest requirements after first-party
validation. The repository reaches six months on November 1, 2026; eligibility
or a submission does not guarantee upstream acceptance.
