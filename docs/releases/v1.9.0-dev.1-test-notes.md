## Reproducible synthetic scenario

1. In disposable inventory, create a 12U rack and a **Stacked switches** device.
   Place it at U1. Add a 2U member named Core A and a 1U member named Core B.
   Enter synthetic model/serial values and a labelled MAC such as
   `02:00:00:00:00:01`. The logical height must become 3U.
2. Create canonical ports `1/1`, `2/1`, and `Console`. Assign the first two to
   their members and leave Console stack-wide. Verify the member filter, front
   and rear faces, and generic layout. No extra ports should appear.
3. Move Core B up using the keyboard. Edit its status and metadata; confirm the
   logical device status does not change. Connect member ports to another device
   and verify selection, anchors, labels, and Rack Studio/Rack Cabling exports.
4. Place a blocker immediately above the stack, then attempt to increase a
   member height. The entire change must fail. Deleting an assigned member or
   changing the populated stack's type must return a conflict. Unassigning its
   ports permits deletion and recomputes the height.
5. Repeat using a custom descendant type. Confirm switch template inheritance,
   role restrictions, cross-lab denial, and preserved assignments after a
   controller refresh. Changing populated stack ancestry must fail.
6. Test room, direct-rack, rack-top, side, and shelf placement. Deleting the rack
   or parent shelf leaves surviving stacks loose with their members and ports.
   Incompatible parent changes and rack shrinking must fail atomically.
7. Export logical/native backups and restore into disposable destinations. Check
   member order, MACs, canonical port/link IDs and assignments. Corrupt ownership,
   order, height, or geometry and confirm the destination remains unchanged.
   Upgrade a genuine schema-50 snapshot: existing switches remain ordinary, and
   ports gain a null assignment. A forged old version marker must be rejected.

## Automated evidence and review

The stack server suite covers CRUD, authorization, ownership, transactional
reordering/resizing, integration preservation, inherited types, Rack Studio,
parent removal, migration failure atomicity, and logical/native restore.
The browser acceptance test covers metadata/MAC editing, keyboard reordering,
assignment/filtering, deletion protection, geometry identity, and accessibility.
The test uses synthetic inventory and writes screenshots only to test artifacts.

Implementation validation on 5 September 2026:

- `check` passed: 307 server tests, 90 client tests, type/lint/i18n checks,
  production build, bundle budget, and 14 Proxmox installer fixtures.
- The stack browser scenario passed, including member-label visibility in the
  rack, canonical port selection and slot coordinates, and byte-identical
  repeated workspace screenshots. The documentation screenshot determinism
  suite passed once, but its final rerun failed on `device-types.png`: 29
  changed pixels (0.00126%), maximum channel delta 17. Its existing tolerances
  were preserved; the intermittent screenshot limitation remains open.
- `check:full` was run twice. Intermittent Vite proxy 502 responses prevented a
  clean full-run result (the last run passed 36 of 38 browser tests). Both
  affected existing tests subsequently passed individually; the complete
  accessibility matrix passed with server diagnostics enabled and no proxy
  error. The intermittent connection failure remains unexplained.
- Compose rendering, Bash syntax checks, ShellCheck, and actionlint passed.
  npm audit and the filesystem security scan reported no findings. The built
  container scan reported 51 high and 3 critical OS-package advisories, none
  with a fixed version available. These findings were not suppressed.
- Independent authorization, migration, invariant, and restore review found
  no remaining actionable defects and independently passed all eight stack
  server tests.
- The original workspace still has ten client typecheck errors in five
  duplicate untracked test files. Those files were preserved; the isolated
  candidate's typechecks passed.

## Recovery

Retain the existing encryption key and a pre-upgrade database/configuration
snapshot. Rollback pairs the previous application with that snapshot. Do not
start an older application against schema 51 or automatically delete backups.
