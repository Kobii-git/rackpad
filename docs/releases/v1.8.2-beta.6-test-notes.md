# Rackpad v1.8.2-beta.6 candidate acceptance

> Historical, unpublished candidate evidence. Superseded by the [combined
> 1.8.3-beta.0 candidate](v1.8.3-beta.0.md). Results and release targets below
> describe the earlier worktree only; they do not validate the combined candidate.

This unpublished candidate is based on the verified `v1.8.2-beta.5` tag. It
addresses native startup readiness (#138) and front/rear cable presentation
(#139), and retains patch-panel authoring (#148). Schema remains 50. No tag,
release, deployment, issue closure, or stable acceptance is implied.

## Changes and compatibility

- Native install, activation, rollback, and snapshot-failure recovery wait up to
  60 seconds for service/HTTP readiness. Retries pause one second; HTTP and
  systemd calls respect the remaining deadline. Terminal service states abort
  early. Existing authentication, SPA, collector, stop, and rollback checks stay
  in place after readiness. Custom ports, trusted hosts, hardening, and safe
  discovery defaults are preserved.
- Front/front and rear/rear routing use the resolved rack face for curve
  eligibility, obstacles, and gutter lanes. Short unobstructed links within 4U
  retain direct curves. The synthetic rear-port case already produced curves on
  beta.5; the reporter's exact failing inventory has not been reproduced.
- Automatic mixed-face links use short continuation stubs at each visible port.
  Hover/select or enable Labels to identify the destination device, port, and
  rack face. Both segments select/trace the same existing cable. SVG/PNG use the
  same geometry. Markers add no ports, devices, links, or stored routing data.
  Existing manual routes keep their previous geometry; brush routing is deferred.
- Patch-panel authoring remains unchanged. Automated coverage includes separate
  front/rear blocks, one row of 24 columns, 48 bindings with zero unmapped slots,
  all 24 pass-through pairs in both directions, custom descendants, and legacy
  face editing. The tester's positive response is partial community acceptance;
  the remaining explicit confirmations are still required before closing #148.

## Upgrade and recovery

Keep the encryption key and a pre-upgrade database/configuration snapshot.
Apply the [schema-50 security upgrade instructions](v1.8.2-beta.4-test-notes.md)
when upgrading from beta.3 or older. Test beta.5 to this candidate on disposable
data, plus the older upgrade paths in the
[beta.5 acceptance matrix](v1.8.2-beta.5-test-notes.md). Do not run an older
application against a newer schema. Rollback after a schema upgrade requires
the previous application and its matching pre-upgrade data/configuration.

and ShellCheck (13 scripts), PowerShell syntax, Actionlint, all three Compose
renders, npm audit, and the repository Trivy scan passed. Independent review of
the readiness and paired-recovery changes found no actionable defects.
`check:full` passed all 37 browser tests, including the responsive, language,
accessibility, and OIDC matrix. The final marker-size/export-count adjustments
also passed the complete standard gate and five focused browser cases covering
routing, SVG/PNG downloads, manual routes/tracing, rack-top placement, patch-panel
authoring, and Device Types.

Both the diagnostic rerun and the normal `screenshots:check` command using
deterministic Chromium compositor/raster settings produced zero changed pixels
across all 40 images on macOS, without changing application styles or comparison
thresholds. Linux CI remains required before publication. Failed captures now
retain their temporary output for diagnosis. These settings follow the
[Chromium rendering flags guidance](https://github.com/GoogleChrome/chrome-launcher/blob/main/docs/chrome-flags-for-tools.md#rendering--gpu).

space; its image scan and container smoke checks remain unrun. A refreshed

`sha256:94fd0bbddacea45ec9184d45241c3bfe02d3b0fb6545bd707e3c54fcecf40a15`.
